### P1-5 一行评论里出现两枚一模一样的主按钮

| | |
|---|---|
| 证据 | `output/cards-live-light.png`（旧）：操作条里「回复」与「折叠」两枚同形胶囊，读起来是两个同级主操作 |
| 判据 | 人工评审 C4 / X1 |
| 修复 | 分层级：两枚都改成**无描边**——**回复**（本行主操作）是一枚纸飞机图标，与楼中楼卡片末尾那枚同一套路径；**折叠**（纯阅读动作）是文字 + 箭头，只有悬停底纹，与站点自己的点赞/回复同一读法；箭头是**状态**（展开朝上、折叠朝下，`aria-expanded` 同一个事实）。两枚随后一起搬进**发言内容之后、楼中楼之前**的右对齐 dock（`.hb-row-dock`）：它们都是「对这句话的回应」，行首操作条留给站点的赞数与楼层；dock 用 `insertBefore` 落在楼中楼容器前，楼层再长也不会把它们顶到区块底部 |
| 复验 | X1 人工评审（`output/award/card-light.png`）；真站 17 条一级评论全部 `dock: 17 / reply: 17 / fold: 9`，`dockPrecedesThread: true`、距正文 10px、距楼中楼 10px、纸飞机右缘与正文容器右缘 `deltaRight = 0` |

> 追加（同一条的后续修正）：把主评论的回复改成图标之后，「回复留描边」这个修复失效了 ——
> 描边原本用来把两枚**同形药丸**分成主次，现在形状已经不同，描边只剩逐行噪音。
> 层级改由墨色承担，见下方 P1-7。

### P1-6 鼠标扫过卡片，卡片当场「散架」

| | |
|---|---|
| 证据 | `npm run verify:cascade` 在本轮改动后判红：hover 前后像素差 **max=44**（阈值 32）。把卡片层与免打扰层关掉再跑同一个测试：**max=4** —— 差异由本层引入。进一步定位（逐像素找 d>32 的热点）：热点是一条 1130px 宽、1px 高的边，颜色从 `rgb(80,85,92)` 变成 `rgb(36,42,49)` |
| 根因 | 站点给楼中楼行画了一层悬停填充：`.link-comment__comment-children .comment-children-item:hover:after{ left:-4px; top:-3px; width:calc(100% + 8px); height:calc(100% + 6px); border-radius:5px; background-color:#f3f4f5 }`。它是**画在同一个元素上的伪元素**，必然排在卡片的背景与描边之上 —— 所以指针一扫过，卡片描边消失、表面被换掉。这不是悬停反馈，是宿主残留规则把卡片拆了 |
| 判据 | U11（新增）、以及原有的 `verify:cascade` |
| 修复 | 在卡片化的行上撤除那层填充（`...comment-children-item.hb-tc:hover::after{display:none}`），改由卡片自己给一个安静一档的反馈：**表面不动、只把描边提亮**（`--hb-ui-edge-hover`）。这是本层第二处隐藏站点节点，与前一处一样只作用于我们加了类的行、关掉开关即还原 |
| 复验 | U11：`::after` display `block`→`none`、表面 `rgb(46,53,61)`→`rgb(46,53,61)`、描边 `rgba(255,255,255,0.16)`→`rgba(255,255,255,0.28)`；`verify:cascade` max=44 → **max=22**（通过，且这条差异正是我们有意加的描边反馈） |

> 这一条是**变异测试之外**的一次真实收获：判据不是想出来的，是先被一个既有回归判红、
> 再逐像素定位出来的。顺带说明另一件事 —— 判据红了要先问「是代码错了还是判据错了」：
> 这里两个都不是，是**两者都对、但缺了一条判据**（没人规定过悬停态归谁管）。

### P1-7 三枚同款纸飞机里，本行主操作反而是最轻的

| | |
|---|---|
| 证据 | 换成图标之后实测三处墨色（真站，深色）：主评论行尾 `#b6bec7`、卡片末尾 `#b6bec7`、折叠 `#9aa3ac` —— 纸飞机两两相同是对的，但**主操作比折叠轻一级**，「回复」在视觉上让位给了纯阅读动作的「折叠」 |
| 判据 | 人工评审 C4（层级），沿用 P1-5 的对象 |
| 修复 | **不加描边**，只用项目既有的墨色阶梯（`--hb-ui-ink` → `--hb-ui-ink-muted` → `--hb-ui-ink-soft`）：主评论纸飞机 `ink-soft` → `ink-muted`。三枚纸飞机因此完全同款，纸飞机与折叠之间差一级 |
| 不加描边的理由 | ① 主评论行尾与卡片末尾的纸飞机常常同屏，给一枚加框就会看出两套同款图标；两处都加框，则 42 张卡片各多一个灰方块。② 描边是**逐行**成本，层级靠加噪表达方向反了。③ P1-5 原本用描边是因为两枚**同形药丸**挤在一处，形状已不同，解法不该照搬 |
| 复验 | 浅色：主评论 `rgb(75,83,89)` = 卡片 `rgb(75,83,89)` > 折叠 `rgb(105,112,119)`，对比度 7.83 / 7.83 / 5.02 均过 U1；深色：7.5 / 6.6 / 5.51 |

## 2. 剩下没修的（诚实清单）

1. **纸飞机离短文本很远。** 卡片层那枚固定在卡片右下角，一行评论只收一条回复时它就贴在右缘。
   试过的替代方案都不如现状：正文是 `flex-basis: calc(100% - 41px)` 独占一行，任何与它同行的项都推不到右边；
   改成绝对定位之外的写法会让它掉到第三行左侧。**保留**，理由：它在 42 张卡片上形成一条稳定的纵向动作列，
   位置一致比位置紧凑更重要；`C4 克制` 不接受为此再加动效。
2. **序号徽标只有 10px。** 这是站点自己的元信息字号，跟随它是「不新造档位」的代价。
   让它更醒目就等于比宿主的正文信息更响 —— 这一层的定位是「不抢戏」。留档待观。
3. **站点自己那条时间/IP 仍是 3.18:1。** 那是宿主的节点与宿主的颜色，本层刻意不碰（碰了就破坏「关掉开关即原样」）。
4. **`折叠` 只藏在内存里。** 换路由或刷新回到展开态（既有取舍，本轮未动）。
5. **卡片里单击正文仍会展开站点的回复框。** 免打扰层把一级评论的「点整行 = 回复此楼」
   收进了一枚明确的「回复」按钮，但楼中楼卡片**刻意没有拦**（当前口径：卡片照常放行，
   回复入口是卡片末尾的纸飞机）。后果是「选中文字」这件事在卡片里只被减了一半：
   **拖拽选中不受影响**（浏览器不会在拖拽后发 click），但**单击一下卡片正文**仍会
   展开 ProseMirror、抢走焦点，把刚建立的选区毁掉 —— 这时只能靠复制解锁层的 3 秒快照救回。
   这是本轮**最大的剩余 UX 不一致**（同一个评论区里，主楼单击=选中、卡片单击=弹框），
   也直接触及这一层的立项理由。改它需要动点击语义并重验 `verify:reply-btn` / `verify:cards`
   的成对判据（「点纸飞机展开一次」不能被拦掉），所以单独一轮做，不夹在这轮里。
6. **主楼操作条里三枚控件的高度是 22 / 24 / 24px**（站点点赞 22，我们两枚 24）。
   2px 的差在截图里读不出来，但严格说不是同一把尺子；若要完全对齐，要么我们降到 22（不达标），要么改站点节点（越权）。取 24。

## 3. 顺带修掉的一条：导航主 CTA 在深色下被判成「浅色泄漏」

跑 `npm run verify:all` 时，实时站点验收 `npm run verify` 在**首页与详情页都失败**：

```
dark.lightSurfaces: 1
lightSurfaceSamples: [{ tag: "button", cls: "login-btn", bg: "rgb(242, 244, 247)" }]
```

**先取证**（`research/probe-login-btn.mjs`）：唯一命中它的、带背景色的规则是

```css
.nav .nav-content .nav-actions .publish-btn[data-v-ab0ef0d9],
.nav .nav-content .nav-actions .login-btn[data-v-ab0ef0d9] { background-color: var(--publish-bg); }
```

值走的是 `var(--publish-bg)` —— 正是引擎文档里写明会跳过的形态（`dark-engine.ts`：
「刻意不匹配 `var(...)`，自定义属性的解析交给 roleOfVar」）。而例外层**早就**处理了这一处：

```css
html.hb-dark .nav { --publish-bg: #f2f4f7; --publish-color: #14191e; … }
```

注释写着理由：浅色下站点把它画成「深底浅字」，深色下反转为「浅底深字」；
引擎判不出「刻意反转的实心 CTA」与「压在图片上的角标遮罩」，所以手工列进例外表。
对照浅色截图确认：**浅色下这个按钮就是深底浅字**（`output/verify/home-light-after-toggle.png`）——
两态互为反相，是刻意设计，不是漏改。

于是这不是代码缺陷，而是**判据与设计意图冲突**：`verify-dark` 的「深色下浅色表面 = 0」
这条规则表达不了「只允许一个刻意反相的 CTA」。处理方式：

- **不放宽判据**：白名单之外仍然要求 0；
- 在 `scripts/verify-dark.mjs` 里把这条意图**写成代码** —— 白名单只含
  `.nav .nav-actions` 下的 `publish-btn` / `login-btn`，命中项单独计数
  （`intentionalLightCta`）并写进报告，且断言 `<= 1`（多一个就红）；
- 备选方案（把深色 CTA 改成深底浅字）是一行改动，但那是**削弱**主 CTA 的可见性，
  且与浅色态不再互为反相 —— 需要产品决定，不在这轮擅自动。

复验：`npm run verify` → home / detail 都 **PASS**，`lightSurfaces: 0`、`intentionalLightCta: 1`。
