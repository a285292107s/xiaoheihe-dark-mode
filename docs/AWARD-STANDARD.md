# 获奖级品质验收标准（Awwwards / Webby / FWA → 本项目）

这份文档回答一个问题：**「这个小黑盒优化脚本插进原站的这一层 UI，凭什么说它够得上获奖级？」**

奖项原文不能直接照抄，因为本项目与它们评价的对象不同。下面第一节把差异说清楚，
第二节把奖项口径翻译成本项目**可度量、可复跑、可判红**的判据，第三节给出打分模型与达标线。

判据编号规则：`维度字母 + 序号`，例如 `D3`、`U7`。代码里与验收脚本里的名字与此一致，
所以「验收报告里红了哪一条」可以直接指回这份文档。

---

## 0. 为什么不能照抄奖项原文

### 0.1 评价对象不同

| | 奖项评价的对象 | 本项目 |
|---|---|---|
| 交付物 | 一个可以整体投稿的独立站点 | 一个注入**别人站点**的样式层（用户脚本） |
| 视觉所有权 | 设计方拥有 100% 的视觉决策 | 底板、字号、栅格、品牌色都是小黑盒的，我们只**叠加** |
| 内容 | 自己写、自己拍、自己排版 | 全是用户生成内容（UGC），我们一个字都不该改 |
| 评委视角 | 首屏 3 秒内的整体印象 | 用户是在**读评论**时顺手看到这一层 |

结论：可以照抄的是**判据的形式**（客观、可量、成对断言、有阴性对照），
不能照抄的是**判据的内容**（例如「Hero 必须首屏放下」在这里不存在）。

### 0.2 本项目里「Design」实际指什么

对独立站点，Design 是「第一眼的整体视觉」。对本项目，Design 是
**「和原站合起来像一个人做的」**：令牌一致、圆角一致、字号一致、层级一致，
以及**可逆**（关掉开关必须字节级回到原样）。这就是 `D` 维度的定义。

### 0.3 本项目里「Creativity」实际指什么

站点原本把「谁回复谁、什么时候、说了什么」挤在一行文本里，头像没有、回复对象时有时无。
把每一行重排成一张卡片、补上头像、补上序号、把悬空的 `:` 补成「回复楼主」——
这是**对既有信息的重新组织**，属于 FWA 口径里的「用新方式组织旧材料」，
而不是视觉上的加特效。所以 `C` 考的是**信息重组是否成立且克制**，不是动画多少。

### 0.4 关键约束：不干扰原站

奖项标准里的「Interactivity」在本项目的对应物是 **不可见性**：
用户不该感知到这个脚本存在，只该感知到「评论区变好读了」。
因此任何判据如果以「更显眼」为方向，在本项目里一律判为缺陷。

## 1. 三个奖项的官方口径（取证）

| 奖项 | 官方口径 | 来源 |
|---|---|---|
| Awwwards | 评委 ≥18 人，四项加权：**Design 40% / Usability 30% / Creativity 20% / Content 10%**；最偏离均值的三位评委分数被剔除；6.5 分以上为 Honorable Mention，Site of the Day 取当期最高分 | [awwwards.com/about-evaluation](https://www.awwwards.com/about-evaluation/)、[utsubo 判据拆解](https://www.utsubo.com/blog/award-winning-website-design-guide) |
| Webby Awards | 七个维度：**Content / Structure and Navigation / Visual Design / Functionality / Interactivity / Innovation / Overall Experience**；其中 Visual Design 明确要求「improving inclusion for people with disabilities, including learning and cognitive disabilities, people with low-vision」；Functionality 明确要求「cross-platform and browser independent」「anticipates the diversity of user requirements」 | [webbyawards.com/judging-criteria](https://www.webbyawards.com/judging-criteria/) |
| FWA | 500+ 评委、35+ 国家；奖励**非常规与实验性**的做法，对「用新方式组织材料」比 Awwwards 更激进 | [utsubo 判据拆解](https://www.utsubo.com/blog/award-winning-website-design-guide)、[webdesignawards.io FWA 评审说明](https://www.webdesignawards.io/awards/fwa) |

三条被反复点名的**失分项**（同样来自上面的来源），直接对应本项目的风险：

1. **无障碍是 Visual Design 的一部分，不是附加项**（Webby 原文写在 Visual Design 条目里）。
2. **跨平台、跨浏览器独立**（Webby Functionality 原文）——用户脚本要活在别人的页面里，这一条比独立站点更硬。
3. **一致性贯穿到每一个页面**，而不只是首页（Awwwards Design 条目）——对应本项目「四个开关 + 五个注入层用同一套令牌」。

补充：所有平台都把**性能**算进可用性（LCP / CLS / INP 是评分的一部分，
获奖目标值为 LCP < 1.5s、CLS < 0.05、INP < 100ms）。
本项目不产生网络请求，性能风险全部集中在**注入字节数与重排**上，所以 `I` 维度按这个口径量。

## 2. 可验收判据（权重与阈值）

计分方式：每条判据 **通过=满分 / 失败=0**；维度得分 = 该维度通过率；
总分 = Σ（维度通过率 × 维度权重）。所有判据由 `scripts/verify-award.mjs` 判定，
**浅色与深色两态各判一次**（两态都过才算过）。人工判据的证据落 `docs/AUDIT-*.md`。

> 判据编号与脚本里的 id 逐字对应；「静态」= 读 `src/*.css` 文本，「运行时」= 在
> `harness/comment-fixture.html` 上注入构建产物后度量。

### D · 视觉与设计系统（权重 30，8 条）

> 对应 Awwwards Design 40%、Webby Visual Design。

| 编号 | 判据 | 度量 | 阈值 | 方式 |
|---|---|---|---|---|
| D1 | **单一令牌源**：两个层文件里不得出现字面量颜色（`forced-colors` 里的系统色关键字除外） | 正则扫描 | 0 处 | 静态 |
| D2 | **令牌跨层同源**：`.hb-reply` 与卡片解析出的 10 项 `--hb-ui-*` 逐项相同 | `getComputedStyle` | 完全一致 | 运行时 |
| D2s | 存在单一共享令牌文件，且三个挂载点（卡片 / 折叠 / 回复）都被覆盖 | 文本 + 引用扫描 | 2/2 引用、3/3 挂载点 | 静态 |
| D3 | **不新造字号**：插入物的字号集合 ⊆ 站点评论区自己的字号阶梯 | 遍历站点节点与自建节点收集 `fontSize` | 阶梯外 0 个 | 运行时 |
| D4 | **圆角成体系**：本层出现的圆角必须落在书面阶梯内（5px 卡片/图标按钮 · 999px 胶囊 · 50% 头像） | 收集全部 `borderTopLeftRadius` | 阶梯外 0 个 | 运行时 |
| D5 | **层级不用投影**：`box-shadow` 只许出现在焦点环上 | 规则扫描 | 0 处越界 | 静态 |
| D6 | **两态层级方向一致**：卡片相对其所在容器都必须更亮（浅色与深色都不许翻转） | 合成底色求相对亮度 | Δ > 0.005（两态） | 运行时 |
| D6s | **深色态不越界改版式**：`html.hb-dark` 块里不许出现布局属性 | 规则扫描 | 0 处 | 静态 |

> **D7 已废止**（2026-10-04，按用户要求移除楼中楼卡片描边）。原判据是「卡片描边对相邻底色
> ≥ 1.4:1」；卡片现在不画描边，边界改由表面差承担（由 D6 守），该阈值没有度量对象，
> 不再计入 D 维度条数与总分。废止记录与复验数据见 [`docs/AUDIT-comment-ui.md`](AUDIT-comment-ui.md) §6。

### U · 可用性与无障碍（权重 30，14 条）

> 对应 Awwwards Usability 30%、Webby Visual Design 的 inclusion 要求与 Functionality。

| 编号 | 判据 | 度量 | 阈值 | 方式 |
|---|---|---|---|---|
| U1 | **可读文字对比度**：本层插入的每一段文字，字色对该处**逐级合成后的**实际底色 | WCAG 2.1 相对亮度 | ≥ 4.5:1（两态） | 运行时·门将 |
| U2a | **图标按钮的图标色**对比度 | 同上 | ≥ 3:1（两态） | 运行时·门将 |
| U2b | **声明了描边的控件**，描边对比度 | 同上 | ≥ 1.8:1（两态） | 运行时 |
| U3 | **目标尺寸**：每个自建控件的外框 | `getBoundingClientRect` | ≥ 24×24（两态） | 运行时·门将 |
| U3b | **行内目标的例外必须真成立**：高度受父行行高约束（≤ 行高 + 2px）且不加内外边距 | 计算样式 + 矩形 | 成立 | 运行时 |
| U4 | **焦点可见**：键盘聚焦每个自建控件都有可见指示，且不是单色 outline | Tab 后读 `outline` / `boxShadow` 层数 | outline 可见或 ≥2 层阴影（两态） | 运行时·门将 |
| U4s | 每个自建控件都有 `:focus-visible` 规则 | 规则扫描 | 4/4 | 静态 |
| U5 | **降级不空窗**：真图 / 降级块两条路都有可见图形 | 矩形 | 均有非零尺寸（两态） | 运行时 |
| U6 | **reduced-motion** 下过渡与位移归零 | `emulateMedia` 后读计算样式 | 全为 0s / none | 运行时 |
| U6s | `prefers-reduced-motion` 块存在且同时归零 transition 与 transform | 规则扫描 | 存在 | 静态 |
| U7 | **forced-colors** 下控件不消失（有真实描边） | `emulateMedia` 后读计算样式 | 全部非 0px 描边 | 运行时 |
| U7s | `forced-colors` 块覆盖每个图标/胶囊控件 | 规则扫描 | 覆盖 3/3 | 静态 |
| U8 | **不溢出**：卡片每个后代的 border box 都落在卡片内容盒内 | 几何度量（**不用 scrollWidth**，见下） | 越界 0 处（两态） | 运行时 |
| U9 | **语义**：自建控件是原生 `<button type="button">` 且有 `aria-label`；纯展示节点不进 Tab 序列 | 属性扫描 | 全部符合 | 运行时·门将 |
| U10 | **极端内容**：超长用户名 / 无空格长串 / 多段正文下卡片不变形、正文列 ≥200px、序号仍在作者行、真换行保留 | 构造输入后度量 | 全部成立 | 运行时 |
| U11 | **悬停反馈由本层定义**：宿主那层 `:hover::after` 填充已撤除；悬停时卡片**表面**给出本层的淡色反馈（`--hb-ui-accent-wash`）；卡片不画描边，描边不参与反馈 | hover 前后读计算样式 | 三件全成立 | 运行时 |

> **U8 的口径为什么是几何而不是 `scrollWidth`**：卡片上常驻一圈透明 outline（引用跳转的高亮环，
> `outline-offset: 2px` + `2px`），Chromium 会把它算进 scrollable overflow，于是 `scrollWidth`
> 恒比 `clientWidth` 大 4px —— 用 `scrollWidth` 判会得到一个恒定的假红（实测 666 → 670）。

## 3. 打分模型与达标线

```
维度得分  V = 该维度通过判据数 / 该维度判据总数
总分      S = 30·V_D + 30·V_U + 15·V_C + 15·V_I + 10·V_X
```

**达标（可以对外说「获奖级」）必须同时满足：**

1. `S >= 90`
2. 五个维度每一个 `V >= 0.85`（不允许用某一维的高分补另一维的短板）
3. 门将判据（`U1 / U2a / U3 / U4 / U9 / C3 / I3`）任一条失败即整体不达标，与总分无关
4. `docs/AUDIT-*.md` 里没有未关闭的 P0 / P1 缺陷

**当前阶段口径**（避免自欺）：人工判据（C4 / C5 / X1）必须附「证据路径」才计入通过，
否则按未通过计。证据 = `output/award/` 下的截图、`output/award/report.json` 里的度量。

**判据本身必须先被验证。** 每次新增判据都要做一次**变异测试**：故意破坏它盯着的那件事，
确认它真的会红。本轮的记录见 `docs/AUDIT-comment-ui.md` §0（6 条判据同时判红，S 从 100 掉到 80.1）。

## 4. 反复自检的闭环

```
① 读标准 → ② 跑 scripts/verify-award.mjs（自动判据）→ ③ 写 docs/AUDIT-*.md（含人工判据证据）
       ↑                                                          ↓
       └────────── ⑥ 重跑全部验收 ← ⑤ 复核 diff ← ④ 只修红的那几条
```

硬规矩（沿用本仓库已有的验收纪律）：

1. **每条判据都要能判红。** 新增判据必须同时证明「不达标时会红」——
   即配一条阴性对照。只写「达标时通过」的判据等于没写。
2. **先取证再改。** 任何「这里不好看」的结论必须落到一个数字或一张截图上，
   否则不许改代码。
3. **改完必须跑全量。** 本层与深色引擎共享 `<html>` 类名，动一层要跑全部。
4. **不许为了让判据变绿而放宽判据。** 放宽阈值必须在这份文档里写明理由与日期。
