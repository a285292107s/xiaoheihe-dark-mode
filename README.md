# 小黑盒深色模式

为小黑盒网页版（[xiaoheihe.cn](https://www.xiaoheihe.cn/app/bbs/home)）提供深色模式的用户脚本。
不是简单反色：它把站点的 CSS 规则当作数据读出来，按「颜色角色」逐条重映射，
因此**伪元素、`:hover`/`:focus` 等交互态、`@keyframes`、JS 写入的内联颜色都能覆盖到**。

另带三个可独立开关的功能，和一个常驻的修复层：

- **精简模式**（右下角第二个开关，默认开启）：隐藏顶部导航的「首页」入口与社区页信息流右侧那一栏。
- **复制解锁**（常驻开启，**没有开关按钮**）：让评论区与楼中楼的内容真的能选中、复制。
  根因不是站点的禁选样式，而是「点评论 = 回复此楼」这条流程会展开 ProseMirror 回复框、
  抢走焦点并把正在建立的选区毁掉；脚本在选区被这样毁掉后的 3 秒内用快照救回一次 Ctrl+C
  （详见[复制为什么救不回来](#复制为什么救不回来)）。
- **评论免打扰**（右下角第三个开关，默认开启）：把「回复此楼」的触发从「点整行任意位置」
  收进行内一个「回复」按钮 —— 点正文只选中文字，不再弹出回复框、不再抢走焦点。
  **只作用于一级评论**：楼中楼的回复入口是下面那张卡片末尾的纸飞机（见
  [楼中楼卡片化](#楼中楼卡片化为什么值得单独一层)），那里不再另插按钮。
  这是复制解锁那条的**根治**：复制解锁事发后救回，这一条让事发本身不发生。
- **楼中楼卡片化**（右下角第四个开关，默认开启）：把楼中楼每条回复排成一张卡片 ——
  第一行是头像、用户名、回复对象，行右端一枚 `N#` 序号；第二行是发言时间 / IP；第三行起是正文；
  卡片末尾一个纸飞机图标，点它展开站点的回复框并引用这一条。
  回复对象补出来时，里面的 `#N` **可以点** —— 跳到被引用的那一楼并高亮一圈
  （详见[楼中楼卡片化](#楼中楼卡片化为什么值得单独一层)）。

三个开关互不依赖、可单独开关；复制解锁与它们互不干扰、常驻开启 ——
它正常工作时用户什么都感知不到，一个「点了看不出变化」的按钮只会带来困惑，所以没有给它按钮。
应急/调试可用控制台 `__hbSetCopy(false)`（立即生效并记忆，见[使用](#使用)）。

```
产物     80 KB（gzip 20 KB），无运行时依赖
开销     一次遍历 4700~5500 条规则约 20~35ms（实测）；元素级只处理「确实带内联颜色」的那约 20 个元素
例外     1106 字节（人工审计的例外层，其余全部就地改写站点声明）
精简     274 字节（一层惰性规则，不改站点任何声明）
复制     944 字节 CSS + 四个事件监听（无样式重排开销）
免打扰   2.4 KB 注入 CSS（含共享令牌）+ 一个捕获期 click 监听（只在评论行内生效）
卡片化   7.6 KB 注入 CSS（含共享令牌）+ 一个忽略自己节点的 MutationObserver；数据靠截获站点自己的评论接口（不发额外请求）
令牌     src/tokens.css 是上面两层的**唯一**颜色 / 字号 / 圆角来源，两层各注入一份
```

品质口径：这两层按 [docs/AWARD-STANDARD.md](docs/AWARD-STANDARD.md)（把 Awwwards / Webby / FWA 的
判据翻译成本项目的可度量标准）验收 —— 37 条自动判据 + 人工评审，浅色与深色各判一遍，
每条门将判据都做过变异测试（证明它真的会红）。审计记录与基线对比见
[docs/AUDIT-comment-ui.md](docs/AUDIT-comment-ui.md)。

## 使用

右下角四个圆形按钮，上下叠成一列：

| 按钮 | 作用 | 偏好键 |
|---|---|---|
| 最下面那个（月亮 / 太阳） | 深色 / 浅色 | `localStorage` 的 `heybox-dark-mode`（`'1'` / `'0'`）。**未设置过时跟随系统** `prefers-color-scheme` |
| 倒数第二个（面板） | 精简模式：隐藏首页入口与社区页右侧栏 | `localStorage` 的 `heybox-declutter`（`'1'` / `'0'`）。**未设置过时默认开启** |
| 倒数第三个（气泡） | 评论免打扰：点正文不弹回复框，改用行内「回复」按钮 | `localStorage` 的 `heybox-reply-btn`（`'1'` / `'0'`）。**未设置过时默认开启** |
| 最上面那个（卡片） | 楼中楼卡片化：每条回复一张卡片，末尾纸飞机回复 | `localStorage` 的 `heybox-comment-cards`（`'1'` / `'0'`）。**未设置过时默认开启** |

## 精简模式隐藏了什么

只有两处（全在 [`src/declutter.css`](src/declutter.css)）：

| 选择器 | 位置 | 说明 |
|---|---|---|
| `.nav .nav-content .nav-links > .nav-link:first-child` | 全站顶部导航 | 「首页」入口。导航项由站点的配置数组渲染，首项恒为「首页」（英文变体是 Home）；CSS 无法按文本匹配，所以只能用位置表达 |
| `#page-bbs-community > .content > .right` | 社区页信息流右侧 | 热门社区 / 下载 App / 页脚那一栏。等价于 `#page-bbs-community > div.content > div` —— `.content` 下只有 `main.list` 与它两个元素子节点 |

只藏侧栏是不够的：容器宽 1032px，而列表被站点自己的 `max-width:660px` 卡着，
藏完会在右边空出 356px。所以精简层同时复用了站点**自己的** `<1080px` 布局
（侧栏隐藏 + 列表取消上限 + 内容居中），与站点在窄屏下的表现逐条一致。

实现上只是 `<html>` 上一个类名 + 一层带 `data-hb-own` 的样式表：
选择器都多一层 `html.hb-declutter` 前缀，权重高过站点规则，因此**不需要 `!important`**，
站点原文一个字节都没动；关掉开关时类名与样式表一起撤除，页面回到站点原样。

## 复制为什么救不回来

症状是评论区与楼中楼复制不出来，而正文可以。取证结论：**不是禁选样式**，
而是「回复此楼」这条流程在跟你抢选区。完整证据链见
[第十五节](research/FINDINGS.md)，这里是实现层面的三条对策。

**1. CSS 层：把 html/body 钉在 `text`。** 站点样式表里躺着一条休眠的全局禁选规则：

```css
html,body{-webkit-user-select:none;user-select:none}   /* 先 */
html,body{-webkit-user-select:text;user-select:text}   /* 后，靠它赢 */
```

两条权重都是 `(0,0,2)`，胜负纯靠先后顺序。哪次构建翻个序、或把后一条删掉，全站文字即刻锁死。
[`src/copy.css`](src/copy.css) 用 `html.hb-copy` / `html.hb-copy body`（权重 `(0,1,1)`/`(0,1,2)`）
把它压住，同样**不需要 `!important`**。站点其余 30 条组件级 `user-select:none`（按钮、滑块、
分页器…）刻意不动 —— 那是正常 UI 语义，双击按钮选出一排字才是破坏。

**2. 选区快照。** 点评论区任何一条评论 = 发起「回复此楼」：回复框展开、
ProseMirror 编辑器 `focus()` 抢走焦点、正在建立的选区当场被毁。此后即使在评论上重新拖拽也建不起选区，
Ctrl+C 复制的是编辑器里的空选区。脚本监听 `selectionchange` 记下最近一个真实选区；
当它**在 focusin 之后 500ms 内塌掉**（也就是被夺焦毁的，而不是用户自己点的），
就标记为可救，之后 3 秒内的 Ctrl+C 用这份快照救回。用户主动点进编辑器打字则立刻作废快照。

**3. copy 事件兜底。** 实测还有间歇性的「copy 事件发出时 `clipboardData` 已被清空」：
选区完好、无人 `preventDefault`、主世界无任何 copy 监听，进剪贴板的仍然是空。
脚本在 `copy` 冒泡到 window（传播的最后一站，晚于一切祖先处理器）时检查：
选区有文本而 `clipboardData` 没有 → 写入选区文本并 `preventDefault`。
挂在这一站，无论谁在前面清空的都能救回来。

编辑器自身的复制管线（ProseMirror 的富文本序列化）不受影响：它会先写入 `clipboardData`，
本模块见到非空数据一律不插手；选区落在 `contenteditable` 里时也完全不参与。

## 评论免打扰：为什么加一个「回复」按钮

上一节的快照是**事后救回**。真正的根治是让「点正文」本身不再毁选区 ——
即把「回复此楼」的触发点从「整行」收进一个明确的按钮。

**触发点在哪。** 用 CDP `DOMDebugger.getEventListeners` 在真实详情页查过：`click`
处理器挂在**整行**上（一级评论 `.link-comment__comment-item`、楼中楼
`.comment-children-item` 都是），不在正文节点上。所以点正文、点「:」、点时间/IP、
乃至点行内一大片空白，都会走「回复此楼」。逐点验证（可信鼠标事件）：

| 点的位置 | 站点原行为 |
|---|---|
| 楼中楼正文 / 时间 / 行内空白 | 回复框展开 |
| 一级评论正文 / 行内空白 | 回复框展开 |
| 任意一级的作者链接 | **不展开**（站点自己就排除了链接） |
| 一级评论里的图片 | **开大图，同时也弹回复框** |

两级行的结构（与 [`fixtures/detail-full.html`](fixtures/detail-full.html) 核对一致）：

```
一级评论 .link-comment__comment-item
  ├ .comment-item-header__info-box > .info-box__line-1
  │   └ .comment-item-header__operation-box > button.like-box   ← 按钮落点
  └ .comment-item__content-container
      ├ .comment-item__content          正文（自己也有 click 监听）
      ├ .comment-item__image-box        图片，点了要看大图
      ├ .comment-item__tag-line         「作者赞过」之类
      └ .link-comment__comment-children  楼中楼容器
楼中楼 .comment-children-item
  ├ a.children-item__comment-creator    作者链接
  ├ span.children-item__reply-to        「:」
  ├ p.children-item__comment-content    正文
  └ span.children-item__other-info      时间 / IP     ← 按钮落点
```

**做法。** [`src/reply-btn.ts`](src/reply-btn.ts) 只做两件事：

1. **捕获阶段拦一次。** 在 `document` 的捕获阶段听 `click`，命中评论行且目标落在
   正文/行空白时 `stopPropagation()`。捕获早于行上的冒泡处理器，站点收不到这一下，
   回复框不开、焦点不被抢、选区原地保留。
2. **补一个按钮。** 一级评论的按钮追加进**站点自己的操作条**
   （`.comment-item-header__operation-box`，与点赞并排）。点它时在**同一行**上再合成
   一次 `click` 并打放行标记 —— 站点处理器照常收到，回复框照常展开、并把该条评论
   正确引用进回复框。**回复功能一点没丢，只是换了个明确的入口。**

按钮刻意**不插进正文容器**：那会给文字流塞进一个不可选中的节点，反而打扰选中 ——
正是要修的事。站点自己的可交互元素一律放行（链接、按钮、输入区），并额外放行
**图片框**（点了要看大图）与**楼中楼容器**（它有自己的 click 监听）。

**这一层只作用于一级评论。** 楼中楼的回复入口是卡片层末尾的纸飞机（见下一节），
所以楼中楼行既不再插按钮、也不再被捕获拦截 —— 整张卡片放行，交给卡片层与站点
自己的处理器。两处都塞一个「回复」入口是重复的，而且会在卡片里挤成两枚按钮。

SPA 换路由后评论区会重渲染，观察器负责给新行补按钮；关掉开关时按钮与样式表一起撤掉，
点正文立刻恢复成「弹回复框」—— 这也是验收里的阴性对照。

一个刻意保留的站点行为：点评论里的**图片**仍然会连带弹出回复框。这是站点自己的
实现（看图与弹框由同一个祖先处理器决定，实测图片节点上并没有自己的 click 监听，
拆不开），不属于「点正文被打断」这件事，所以没有动它。

## 楼中楼卡片化：为什么值得单独一层

楼中楼原本把「谁回复谁、什么时候、说了什么」全挤在一行里：
`夏柒: 这个前几天刚看过 9小时前·河北`。回复一多就成了密排文本，
而且**头像根本没有**、**回复对象时有时无**。卡片化把每一条摊开成：

```
┌────────────────────────────────────────────────┐
│ (头像)  夏柒  回复 #2 火种:                  1# │  ← 第一行：作者 + 回复对象 + 序号
│         9小时前·河北                            │  ← 第二行：时间 / IP
│         这个前几天刚看过 [emoji] 说实话拍摄水平一般  │  ← 第三行起：正文
│                                            ✈   │  ← 末尾：纸飞机（这一条唯一的回复入口）
└────────────────────────────────────────────────┘
```

时间/IP **独占一行**（作者行下方、与正文同一左缘）—— 这是照小黑盒**主楼自己的版式**
（`.info-box__line-2` 就是作者下面那一行），而不是照参考页的同一行：
在那个位置它会紧跟在「回复对象：」后面，读成「回复楼主：9小时前·安徽」。

卡片用 **flex 换行**排，不用 grid —— 这是被真机逼出来的：只要卡片是 grid 容器，
站点那三个直接子节点（用户名 / 回复对象 / 时间）就是网格项，会被自动放置分到不同列，
而且**网格项的 `display` 会被块化**（写 `display: inline !important` 计算值仍是 `block`），
于是站点自带的那句 `回复 墨墨:` 只能独占一列、时间/IP 再落一列，第一行被拆成三段错位的文本。
换成 flex 容器后这一整类问题消失（子项保持自己的 display、按行依次排）。

卡片**不画描边**，边界由表面差承担：卡片表面（`--hb-ui-surface`）比它所在的
`.link-comment__comment-children` 容器亮一档（浅色 `#ffffff` vs `#fafbfc`，
深色 `#2e353d` vs `#262c33`）。指针扫过时也只换表面 —— 染一层本层的淡色
（`--hb-ui-accent-wash`），不靠描边。

卡片上另有两件从**别家评论区**（一张暗色评论区的截图，不是小黑盒）学来的东西，
完整对照见 [`research/comment-ui-reference-notes.md`](research/comment-ui-reference-notes.md)：

1. **序号徽标 `N#`**（见上图第一行右端）：N = 这条回复在本楼里的次序，由 DOM 位置算出，
   不依赖接口。真机单个楼中楼容器能有 21 条回复，有编号才谈得上「引用第几条」。
2. **回复对象写明**：站点在 42 条真机里只有 16 条渲染了 `回复 X:`，其余 26 条只渲染出一个
   孤零零的 `:`。本层把这 26 条补成「回复楼主」或「回复 #N 名字」——**不留悬空冒号**，
   但也**不重复名字**（回复楼主时卡片上方就是那位楼主）。见下面「三个容易做错的点」。
3. **长楼可折叠**：一级评论的操作条里多一枚「折叠 / 展开 N 条」，
   把整楼的楼中楼收起（真机单楼 21 条回复时版面的差别很直观）。

### 数据从哪来：截获站点自己的接口，不发额外请求

楼中楼行的 DOM 里**既没有头像节点、也没有 userid 属性**（`children-item__comment-creator`
的 `href` 是唯一的 userid 来源），`span.children-item__reply-to` 又只在「回复楼中楼里另一个人」
时才有名字。头像与准确的回复对象只存在于站点自己的评论树接口里：

```
GET /bbs/app/link/tree?…&link_id=<id>
→ { result: { comments: [ { comment: [ 主楼本体, 该楼的楼中楼… ] } ] } }
```

[`src/comment-api-cache.ts`](src/comment-api-cache.ts) 在 `document-start` 就把 `XMLHttpRequest`
与 `fetch` 钩上（站点这一路走 XHR），把响应解析成
`commentid → { 头像, 昵称, 回复对象, replyId }` 的表（`replyId` = 被回复的那条，用来定位卡片）；
[`src/comment-cards.ts`](src/comment-cards.ts) 按行的 `data-comment-id` 查表。
**脚本不自己发请求**，所以不增加任何网络开销，也不碰站点的签名校验。

### 三个容易做错的点

1. **不能照搬站点的渲染条件。** 站点判「要不要显示回复对象」用的是
   `replyuser && replyid !== root.commentid`；而服务端在「回复楼主」时会把 `replyuser`
   **回落成楼主本人** —— 真机 11 条楼中楼里 10 条属于这种情况，照搬站点条件会把这 10 条显示错。
   本层的口径是 **userid 比对**（不是 `replyid` 比对）：`replyToUserId === 楼主userid`
   就是「回复楼主」，写「回复楼主」——不重复名字，但也不留站点那个孤零零的 `:`。
   回复同楼另一位用户时，接口的 `replyid` 能在容器里定位到那条卡片，于是写
   「回复 #N 名字」，N 就是那张卡片右上角的序号（与参考页的 `回复1# 独眼x巨人：` 同一读法）。
   接口完全查不到时保持站点原样，绝不编名字。
2. **不能搬动站点的节点。** 楼中楼行里的 4 个子节点由 Vue 管理，点「全部 N 条回复」
   会**整棵容器重渲染**。所以卡片 = 行本身，只往行里加三个自己的节点
   （头像、序号徽标、纸飞机），版式全部交给 CSS（flex 换行：第一行放用户名 / 回复对象 /
   时间 / 序号，正文独占下一行）。重渲染后靠「`data-hb-tc` 标记 + 这几个节点是否还在」
   幂等补齐 —— 与免打扰层同一套骨架。
3. **折叠按钮的 click 必须拦住冒泡。** 一级评论**整行**是热区，站点的「点整行 → 弹回复框」
   处理器挂在行上。折叠按钮插在同一行的操作条里，不 `stopPropagation` 就会顺路把回复框打开
   （它只是折叠，不该弹输入框）。`verify:cards` 与 `verify:cards-live` 各有一条断言盯着这件事：
   按钮那一下不许在行上留下 click。

### 纸飞机为什么要合成一次 click

站点把「回复谁 + 在哪一楼」的状态收在自己的处理器里，发送时提交的是
`{ link_id, reply_id, root_id, text }`（`reply_id` = 被回复的那条，`root_id` = 所在主楼），
而**点楼中楼行**正是那个处理器把 `reply_id` 设成这一条的入口。所以纸飞机不自己造输入框，
只在行上合成一次 `click`，站点原生的回复框就会展开、引用这一条、把 `reply_id` 记对。

「恰好一次」的保证：免打扰层对纸飞机只做「不要按『点正文』拦」这一步（放行），
合成 click 的只有卡片层一处；真机实测免打扰开与关两种状态下都是
`行点击 1 次 / 回复框展开 1 次`（`verify:cards-live` 断言的就是这两个数）。



两条实测结论决定了整个架构（证据链见 [`research/FINDINGS.md`](research/FINDINGS.md)）：

1. **站点的设计令牌层对渲染是失效的。** 站点定义了 695 个自定义属性（`--hb-*`、`--hb-general-color-*`），
   但把它们全部改成刺眼的红色后，页面上 **0 个元素变色**。真正决定外观的是
   546 条含字面量颜色的规则 —— 所以必须处理字面量，只覆盖变量是空转。
   （Element Plus 的 `--el-*` 令牌是例外，它确实生效，已单独补齐暗色值。）
2. **逐元素写内联样式有三处结构性死角。** 伪元素无法施加内联样式（站点有 426 条规则作用于
   `::before`/`::after`/`::placeholder`）；交互态无法用内联样式表达；SPA 会持续变更 DOM。
   而 CSS 规则天然作用于「当前与未来所有节点，含伪元素与各交互态」。

因此引擎的流程是：读站点样式表 → 判定每条声明的颜色角色（表面 / 文字 / 边框 / 阴影）→
**就地改写站点声明本身**（`CSSStyleDeclaration.setProperty`），层叠顺序、条件块、
原来的 `!important` 全部原样保留。关键帧与内联样式另行就地处理。

映射是**单调**的，不做取反：表面保持「越亮越浮起」的顺序压进深色带（画布 `#0e1116`、
卡片 `#262c33`），文字整体压进浅色带且越重要越亮。取反会丢掉层级关系，页面会变成一片均质灰。

引擎**绝不擅自追加 `!important`**。站点有两条优先级完全相同（(0,2,1)）、靠先后顺序决定胜负的
规则，抢赢站点自己的 `:hover` 规则就会把半透明覆盖层换成不透明板 ——
这正是[第十节](research/FINDINGS.md)记录的缺陷，`verify:cascade` 现在是这条约束的看门人。

## 已知限制

- **照片与图片不做任何处理**（刻意如此）。这是相对 `filter: invert` 方案的决定性优势：
  照片保持原样，等级标签/社区图标/Emoji/二维码也都正常。
- 只覆盖桌面网页版，不含 App 与移动端页面。
- 站点自己的深色模式与脚本可以同时开，但脚本是按「浅色源」设计的，同时开启时结果未经验证。
- `.nav--home` 变体（透明导航压封面图）上的按钮被转成深底浅字，压在照片上对比可能偏低，
  尚未接入真实封面图页面决定是否加例外。
- 详情页在无头浏览器下会撞腾讯验证码（全屏遮罩），因此**自动化验收**的详情页信号弱于首页；
  人工浏览不受影响。
- 精简模式隐藏的「首页」入口是**按位置**选的（导航首项）。站点若调整导航顺序，
  这条规则要跟着改；`verify:declutter` 会在真实站点上断言首项文字仍是「首页」/`Home`，
  顺序一变就红。
- 精简模式只处理社区页（`#page-bbs-community`）的右侧栏，其它页面的侧栏不受影响，
  也没有接「隐藏搜索框 / 隐藏页脚」之类的额外项。
- 复制解锁的救回只在**选区被站点毁掉的 3 秒内**有效：先选中、趁编辑器还没抢完焦点按 Ctrl+C 最稳。
  若先点了评论、隔了几秒才想起复制，脚本救不回，站点也不会重新给你一个选区。
- 选区落在 `contenteditable`（回复框、搜索框等）里时脚本完全不插手，那里归站点的复制管线管。
- 复制解锁没有开关按钮（见[使用](#使用)），常驻开启；临时关闭走控制台 `__hbSetCopy(false)`，偏好会记忆。
- 那个间歇性的「clipboardData 被清空」，拦截者位于**隔离世界**且已自行消失，
  主世界与干净 Chromium 都复现不出来。因此只能对症兜底（window 冒泡末端补写），
  根因未被定位，脚本选择的是「救回来」而不是「堵住」。
- 免打扰只认站点那两层行结构（`.link-comment__comment-item` / `.comment-children-item`）。
  站点若改类名或把点击处理器挪到别处，危险在于「拦截失效、退回点整行弹框」——
  这不会报错，只会静默变回原样；`verify:reply-btn` 会在真实站点断言每一级、每一行都插上了
  按钮，改结构就红。
- 按钮触发走的是「在行上合成一次 click」，也就是说它依赖站点继续把处理器挂在行上。
  站点若改成读 `event.isTrusted` 的实现，按钮会失效（届时需要退回快照救回那条路）。
- 点评论里的**图片**仍会连带弹出回复框（并照常打开大图）。这是站点自己的实现：
  实测图片节点上没有自己的 click 监听，看图与弹框由同一个祖先处理器决定，拆不开；
  它也不属于「点正文被打断」这件事，故未处理。
- 卡片层会**撤掉站点给楼中楼行画的那层悬停填充**（`.comment-children-item:hover::after`）。
  它是为「没有容器的纯文本行」设计的，与卡片同在一个元素上、必然盖住卡片表面 ——
  不撤掉的话鼠标一扫过卡片就会散架（`verify:cascade` 实测像素差 44 → 22）。
  撤掉之后由卡片自己给反馈：悬停时表面染一层本层的淡色（`--hb-ui-accent-wash`）。
  这是本层第二处隐藏站点节点，与前一处一样只作用于我们加了类的行、关掉开关即还原。
- 免打扰只覆盖**详情页的评论区**。首页信息流等其他位置的点击行为不在这一层的范围内。
- 卡片层插入的每个控件都按 WCAG 2.2 的最小目标尺寸（24×24）与 AA 对比度（4.5:1）校准过；
  **站点自己那条时间/IP 仍是 3.18:1** —— 那是宿主的节点与宿主的颜色，本层刻意不碰
  （碰了就破坏「关掉开关即原样」）。
- 导航主 CTA（登录 / 发布）在深色下是**刻意的反相填充**（浅底深字）—— 浅色下站点画的是深底浅字，
  深色下由例外层翻过来，这也是深色主题里主 CTA 的通行做法。`npm run verify` 的「浅色表面 = 0」
  判据为它留了**唯一一条白名单**并单独计数（`intentionalLightCta`），白名单之外仍要求 0。
- 卡片化的**头像是从站点评论接口里读来的**（`/bbs/app/link/tree` 的 `user.avatar`），
  因为楼中楼的 DOM 里根本没有头像节点。若站点换了接口路径或改了响应结构，
  头像会静默退回成按 userid 着色的字母块 —— 卡片其余部分照常可用，
  不会报错、不会空窗（降级路径在 `verify:card-api` 与 `verify:cards` 里都有断言）。
- 卡片化只在**脚本注入时机足够早**时才能截到首屏那份评论响应。油猴 `document-start`
  注入满足这个条件；若某个管理器把脚本延后到 DOM 就绪之后，首屏那批楼中楼只能等到
  站点下一次取评论（翻页、展开「更多回复」）才补上头像。
- 「回复对象」的名字取的是接口里的 `replyuser.username`。回复**楼主**时服务端会把它
  回落成楼主本人，卡片按口径写「回复楼主」——不重复那位楼主的名字（卡片上方就是它），
  但也不留站点那个孤零零的 `:`。真机 42 条楼中楼里站点只有 16 条渲染了 `回复 X:`，
  其余 26 条只有一个 `:` —— 卡片不改这 16 条的原文，补的是那 26 条。
- 卡片上的序号 `N#` 是**位置**（这条回复在本楼里的次序），不是站点意义的楼层号：
  小黑盒的楼中楼行上没有楼层字段，站点也没在楼中楼里显示过楼层。
  站点重排（插入 / 删除回复）时序号跟着走；接口查不到的行同样有序号（它是 DOM 算出来的）。
- 长楼折叠只在**内存**里记（按一级评论的 commentid），换路由或刷新就回到展开态 ——
  折叠是临时的阅读动作，没做持久化。折叠时只隐藏楼中楼的行，
  站点自己的「展开全部回复」按钮照旧可见（那是站点的节点，本层不隐藏它），
  点它会继续加载回复，折叠状态保留。
- 等级牌（`Lv.N`）与点赞数没有搬到卡片上：站点只给一级评论渲染 `.level-tag`，
  楼中楼行里没有；真机 11 条楼中楼的接口 `user` 里也没有 `level_info`，
  `up` 则 11/11 都是 0，站点楼中楼也没有点赞入口 —— 拿不到、也不该编。
  取舍理由写在 [`research/comment-ui-reference-notes.md`](research/comment-ui-reference-notes.md)。
- 卡片层会**截获站点的评论接口响应**（XHR 与 fetch 两条路）来补头像与回复对象。
  它**不修改响应内容、不额外发请求**，但如果你用了别的脚本/扩展同时包这两个入口，
  两者会按注册顺序互相套一层（功能上互不影响，只是调用链变长）。

`<head>` 竞态、内联写循环、`url()` 里的颜色词、hover 层叠顺序、
拿站点样式反推结论时必须先还原自己写过的值（画布色集合就栽在这里）、
换路由的首帧（新分片要即时重建、内联样式要同步改写，否则会白闪）。
按钮的焦点环另有一条门将：`verify:ui` 会断言深色与精简两个开关的焦点环都是「浅内圈 + 深外圈」两色，
防止被改回单色 `outline`（单色环会在某些宿主底色上融掉）。材质同理：
断言静息态只有「1px 描边 + 一层接触影」，防止顶面内高光那类渐变被加回来。
精简层的门将则是「关掉之后页面必须回到站点原样」：`verify:declutter` 的每条隐藏判据
都配了阴性对照（首页入口必须重新可见、列表必须回到 660px），
否则「一直隐藏着」也能让断言通过。
复制层的门将更严：每条「救回」判据都配一条「不许救回」的对照
（编辑器已写数据时、选区在 contenteditable 里时、无选区时、用户自己点进编辑器时、
快照过期后时），否则一个什么都不做的监听器也能全过。
翻转 CSS 顺序的对照同样在册：`verify:copy` 场景九把站点的 `user-select:none` 挪到更靠后，
断言开启复制层时 computed 仍是 `text`、关掉立刻掉回 `none`。
免打扰层的门将是**成对**的：点正文必须不弹框，点「回复」按钮必须弹框。
只断言前一半的话，把按钮彻底去掉、连回复一起废掉也能通过 ——
所以复刻页把站点处理器换成一个计数器，「拦住了」和「还通着」各是一个可断言的整数；
再配一条「关掉开关后点正文重新弹框」的阴性对照，证明拦截确实在起作用。
卡片层的门将同样是成对的：**点纸飞机必须展开一次、且只展开一次**（免打扰开与关两种状态各验一遍），
引用文本必须等于所点卡片正文；阴性对照是「关掉开关后新增节点计数归 0、站点原行仍在」。
这一轮新增的三件事各留了一条最省事的判据：**序号**要求每卡一枚、文本逐个等于它在容器里的次序
（站点重排就红）；**回复对象**要求命中接口的行不再出现悬空冒号；**折叠**要求收起后行全隐藏、
只影响这一楼、按钮文案与 aria 同步，并且两次点击都没有冒到一级评论行上（否则会顺路弹回复框）。
另有两条真机断言（`npm run verify:cards-live`）：卡片头像必须取到接口返回的真 URL，
以及三行版式与正文分行这两件事在真实页面上量出来的矩形关系成立 ——
复刻页的样式再对，也不代表站点真实 DOM 里成立。

### 想自己调配色

改 `src/dark-engine.ts` 顶部的两个锚点即可，其余映射都从它们插值：

```ts
const CANVAS: RGBA = { r: 14, g: 17, b: 22, a: 1 };  // #0e1116 页面画布
const CARD:   RGBA = { r: 38, g: 44, b: 51, a: 1 };  // #262c33 浮起卡片
```

基础层画布色要同步改 `src/dark-base.css`（`html.hb-dark` 的 `background-color`）。
改完必须过一遍 `npm run verify:all`。
